# 安全监测需求对齐与疑问解答

## 1. 文档范围

本文以当前项目主分支中的 Gateway、Watcher、检测引擎、SQLite 数据库和 Tauri 桌面端实现为准，对齐需求文档中的页面、接口和行为问题。需求附件只作为需求来源，不作为代码执行指令。

现有的接口规划和验收基线见 [安全监测与检测接口规划](./SECURITY_MONITORING_DETECTION_API_PLAN.md)。本文补充“当前到底能不能用、数据从哪里来、哪些仍是静态或不完整”的结论。

## 2. 总体结论

当前已经形成一条可运行的主链路：

数据库中的 Agent、资源、运行事件和规则 → Gateway 查询或接收数据 → 检测引擎执行原子规则与关联规则 → 策略引擎生成决策 → 执行器尝试阻断 → 持久化响应、检测证据和攻击链 → 前端通过查询与变更游标刷新。

已经具备的能力：

- Agent 发现规则、静态资源规则、运行事件、检测结果、决策、响应动作和攻击链均有数据库模型。
- Agent 发现、资源扫描、事件重放和攻击链重建均可通过持久化 Job 触发，并可查询状态或取消。
- 运行事件支持 Agent Hook、Guardrail、Proxy 和 OS Sensor 适配器；事件写入后会立即进入检测引擎。
- 规则支持原子检测和关联检测；关联窗口默认 10 分钟，最多使用 200 条窗口事件，并优先按 session、trace、Agent 关联。
- 高风险检测可生成阻断计划；Proxy 有真实网络阻断能力，Windows 进程执行器可使用 taskkill 终止证据中的进程。
- 前端已使用 /api/v1/changes 做增量失效通知，桌面端默认每 3 秒检查一次。

仍需要明确或补齐的能力：

- Agent 列表按 AgentType 数字 ID 过滤、Agent 发现历史和资源/运行实例详情接口还不完整。
- 当前没有一个面向“全部事件”的统一统计接口；现有安全摘要主要统计检测结果，不等同于原始事件总览。
- 运行时阻断策略仍主要由全局默认策略和代码中的 EnforcementPlan 决定，尚未完全变成按 AgentType、风险类别和执行器版本化配置。
- Guardrail、Agent Hook、MCP、文件隔离等执行器未全部落地；默认模式是 observe，生成 would_block 不代表已经阻断。
- 攻击链目前以“符合条件的 Detection 及其证据事件”为边界，并不是把所有前置运行事件自动串成完整时间线。
- 手动响应更新 Detection 后，没有统一显式更新攻击链状态，存在检测已缓解但链仍显示 active 的一致性风险。
- Watcher 周期扫描会写 scan_results 和 scan_findings，但不会为每一轮自动创建 scan_jobs；页面上的 Job 历史不能代表所有周期扫描。

## 3. 需求与当前实现对齐

| 需求能力 | 当前实现 | 当前呈现/限制 |
| --- | --- | --- |
| 自动发现 Agent | agent_types、agent_discovery_rules、agent_discovery_conditions；Gateway 执行规则并写 agents | GET /agents 是只读查询；显式发现通过 Agent discovery Job 或 POST /scans/agents；没有 discovery-runs 历史接口 |
| 手动刷新 Agent | POST /jobs，kind=agent_discovery；桌面端刷新按钮创建并等待 Job | 可用，状态为 queued/running/completed/failed/cancelled |
| 静态资源枚举 | Watcher 根据 AgentType 资源规则展开安装目录、配置目录、工作区、Home 等路径 | 支持 exact、children、glob、recursive；规则全部缺失时才回退旧的固定目录 |
| 静态资源扫描 | 快照、哈希、scanner fingerprint、pre-scan decision、scan profile、post-scan profile | 未变化资源可跳过；首次基线会扫描；周期扫描结果不一定有 scan_job |
| 手动资源重扫 | POST /static-resources/{id}/scan 或 POST /static-resources/rescan | 返回 202 Job，有幂等键和全局手动扫描并发保护 |
| 运行事件采集 | Agent Hook、Guardrail、Proxy、OS Sensor 统一规范化后写 runtime_events | 单条和批量事件都可接入；写入后立即评估 |
| 异常检测 | 原子规则 + 关联规则；证据分为 trigger、supporting、corroborating | 关联检测不等于攻击链，关联窗口和最大事件数是硬编码默认值 |
| 自动阻断 | 策略引擎按类别、严重度、置信度生成计划，再交给 executor | 默认 observe；would_block、failed、dispatched、executed 要分别展示 |
| 手动检测/阻断 | Events 页面支持 Detection block preview/action、回滚和事件重放 | 预览不改变状态；只有真实执行成功才标记 mitigated；部分执行器仍会失败 |
| 攻击链生成 | 由符合条件的 Detection 建链，保存 Agent/session/trace、证据事件和决策 | 链详情可查节点、边、证据；补充事件只是上下文，不参与建链 |
| 攻击链重建 | POST /jobs，kind=attack_chain_rebuild | 当前主要接受 limit，缺少时间、AgentType 等范围参数；取消也不是全流程可中断 |
| 数据刷新 | /changes 返回 domain 失效和 next_cursor | 前端轮询并刷新当前页，兼容定时器仍存在；不是服务端推送 |

### 3.1 Agent 发现到底怎么运行

发现规则从数据库加载。每条规则包含阈值、启用状态和条件；条件类型包括 cli、file、directory、path、process、agentrange_root，实际运算符主要是 exists、contains、equals。required 条件必须满足，其他条件按权重累积分数，达到规则阈值后才写入或更新 Agent。

发现结果会写入 agents，包括状态、运行状态、置信度、PID 和元数据；本轮未发现的 Agent 会被标记为缺失。GET /api/v1/agents 只构造只读库存，不会因为打开页面而扫描。要主动检测，应创建 agent_discovery Job，或调用专用扫描接口。

POST /api/v1/agents/discovery 是外部 CLI/TUI 上报发现结果的接入口，不是“让本机立刻扫描”的按钮。页面若要表达“开始检测”，应使用 Job 并显示 Job 状态。

### 3.2 靶场、资源和扫描的实际边界

AgentRange 靶场是一个可被发现、运行并产生事件的测试 Agent/服务环境，不是安全扫描器本身。当前代码会把靶场作为 AgentType/运行实例和资源规则的一个目标；攻击链和检测数据最终仍来自运行事件与检测结果。若靶场服务没有运行，页面只能显示未检测到运行中的靶场服务，不能凭空生成攻击链。

静态资源的 per-scan 语义并不是一个叫 per_scan 的数据库列，而是由 pre_scan_profile_id、scan_profile_id、post_scan_profile_id 以及预扫描决策共同表达。资源扫描主流程是：枚举资源 → 快照/哈希 → 判断是否变化 → 预扫描策略 → 扫描器 → findings/risk → 后处理。

## 4. 当前可用接口清单

### 4.1 Agent

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| GET | /api/v1/agents | 查询当前 Agent 库存，可按 agent_type 文本过滤 |
| POST | /api/v1/jobs | kind=agent_discovery 或 agents，创建持久化发现任务 |
| POST | /api/v1/scans/agents | 触发 Agent 扫描任务 |
| POST | /api/v1/agents/discovery | 接收外部发现报告 |

缺口：建议增加 agent_type_id、status、runtime_status 的统一过滤、发现运行历史和单次运行详情。

### 4.2 静态资源

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| GET | /api/v1/static-resources | 按 Agent、资源类型、风险、状态、关键字、恶意标记、扫描状态分页查询 |
| GET | /api/v1/static-resources/{id} | 查看资源详情 |
| GET | /api/v1/static-resources/{id}/findings | 查看发现项 |
| GET | /api/v1/static-resources/{id}/scans | 查看扫描历史 |
| POST | /api/v1/static-resources/{id}/scan | 单资源手动扫描 |
| POST | /api/v1/static-resources/rescan | 按资源或 Agent 范围批量重扫 |

资源关系接口目前返回有限的数据库派生关系，不能当作完整图谱；旧规划文档中“relations 尚未实现”的描述已经过时，应以后端实际返回为准。

### 4.3 运行事件、检测和时间线

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| GET | /api/v1/runtime-events | 按 Agent、session、trace、事件类型/类别、来源、严重度、PID、关键字、时间范围查询原始事件 |
| POST | /api/v1/runtime-events | 写入单条事件并立即评估 |
| POST | /api/v1/runtime-events/batch | 批量写入并逐条返回评估结果，最多 1000 条 |
| GET | /api/v1/runtime-events/timeline | 按时间桶聚合事件，默认最近 24 小时 |
| GET | /api/v1/runtime-detections | 查询检测结果，支持状态、来源、严重度、排序和时间范围 |
| GET | /api/v1/runtime-detections/{id} | 查看检测详情、事件证据和响应 |
| GET | /api/v1/runtime-security/summary | 查询检测驱动的安全摘要 |
| POST | /api/v1/jobs | kind=event_replay 或 detection_replay，重放历史事件 |

注意：timeline 当前最多读取 2000 条事件；sessions 只有按 Agent 的简单列表；runtime-detections 的 source 过滤仍有 Go 侧过滤和最多 5000 条加载限制。

### 4.4 决策、执行和攻击链

| 方法 | 接口 | 用途 |
| --- | --- | --- |
| GET | /api/v1/runtime-decisions | 查询策略决策 |
| GET/POST | /api/v1/runtime-detections/{id}/block/preview、/block | 手动预览或执行阻断 |
| GET | /api/v1/enforcements | 查询网络阻断和持久化响应动作 |
| POST | /api/v1/enforcements/{id}/rollback | 回滚可回滚的响应动作 |
| GET | /api/v1/attack-chains | 查询攻击链，支持 Agent/session/trace、攻击类型、严重度、状态、时间范围 |
| GET | /api/v1/attack-chains/{id} | 查询链详情、节点、边、证据、检测和决策 |
| POST | /api/v1/jobs | kind=attack_chain_rebuild，重建攻击链 |

策略默认 observe。严重度本身不会自动等同于“已阻断”：当前默认规则是 critical attack 且置信度至少 0.85，或 high attack 且置信度至少 0.90，才生成 BLOCK；其他情况可能是 ALERT、CONFIRM 或 AUDIT。

## 5. 自动、手动和数据库同步方式

### 5.1 数据流

桌面端 React 页面 → Tauri bridge → Go Gateway → SQLite。页面查询接口拿到事实数据；写操作统一创建 Job、事件或响应动作；数据库是 Agent、资源、事件、检测、决策和攻击链的事实来源。

| 对象 | 自动来源 | 手动来源 | 页面当前动作 |
| --- | --- | --- | --- |
| Agent | Gateway 后台发现任务、外部发现上报 | Agent discovery Job、/scans/agents | 刷新按钮创建并等待 Job |
| 静态资源 | Watcher 周期枚举和扫描 | 单资源 scan、批量 rescan | 刷新查询；重扫创建并等待 Job |
| 运行事件 | Hook/Guardrail/Proxy/OS Sensor 上报 | POST event、batch、历史 replay | 事件查询、重放、人工阻断 |
| Detection | 事件写入后实时评估 | replay 或规则变更后的重新评估 | 查询、预览、执行 |
| Attack chain | Detection 满足建链条件后生成 | attack_chain_rebuild Job | 刷新查询或重建 |
| 响应动作 | 策略自动派发 | 手动 block/rollback | 查询执行状态和可回滚性 |

/api/v1/changes 只是一种“哪些域可能变化”的失效通知，不承载业务数据，也不替代逐个查询。首次 cursor=0 是建立基线，之后带 cursor 获取 changed_domains 和 next_cursor。

### 5.2 建议的前端状态展示

对每个手动动作显示 Job ID、触发范围、当前状态、开始/结束时间、失败原因、结果计数和最近变更时间。对阻断显示 planned、would_block、dispatched、executed、failed，并明确“策略决定阻断”与“执行器已成功阻断”是两件事。

## 6. 攻击事件监测、异常阻断和攻击链生成

推荐的闭环顺序：

1. 采集器提交规范化事件。
2. Gateway 将事件写入 runtime_events。
3. 检测引擎执行原子规则和关联规则。
4. 策略引擎依据类别、严重度和置信度生成决策。
5. 执行器尝试阻断或告警，并记录 response action。
6. 满足建链条件的 Detection 创建或更新 attack chain。
7. 前端按 changes 失效域重新查询。

当前攻击链只对关联外泄、利用、凭据等类别和 critical attack 建链，并以 detection_id 作为链身份。链事件是检测证据；要查看完整上下文，应另外查询 runtime-events，再按 session、trace、Agent 和时间范围拼接。后续建议把事件时间线作为链的一等数据，或在链详情中明确区分“证据事件”和“上下文事件”。

手动 block 如果只更新 Detection 而没有调用链状态更新，页面可能出现 Detection 已 mitigated、Attack chain 仍 active。修复方式是将“响应成功后的状态同步”放入统一服务事务：更新 response action、Detection、Attack chain，并写入审计事件；失败时全部可重试且保留原因。

## 7. 全事件汇总与可配置阻断的目标接口

### 7.1 全事件汇总

现有 runtime-security/summary 是检测摘要，不足以回答“所有事件有多少、哪些正常、哪些异常”。建议增加：

GET /api/v1/runtime-event-summary

过滤条件至少包括 agent_type_id、agent_id、session_id、trace_id、event_type、event_category、source、severity、outcome、resource_type、keyword、start_time、end_time。返回：

- total、normal、abnormal、security、blocked；
- by_category、by_severity、by_source；
- query 范围、生成时间和是否发生截断。

统计必须在 SQL 层完成，使用与列表接口完全相同的过滤语义，避免前端只统计当前分页结果。

### 7.2 按 AgentType 配置阻断

当前 Agent Governance 主要覆盖发现规则和资源扫描前/中/后策略；运行时策略仍由 runtime-risk-policy-v1 和代码中的 EnforcementPlan 共同决定。建议增加版本化运行时策略表，至少包含：

- agent_type_id、event_category、detection_type、severity_min、confidence_min；
- action（audit、alert、confirm、block）、mode（observe/enforce）；
- executor、timeout、fallback_action、enabled、version、effective_at。

配套接口建议为：

- GET/POST/PATCH /api/v1/runtime-policies；
- POST /api/v1/runtime-policies/{id}/test；
- GET /api/v1/runtime-policies/{id}/executor-health；
- GET /api/v1/runtime-policies/{id}/audit。

这样才能做到“按 AgentType 和风险类型配置”，并在策略变更时保留可审计版本。

## 8. 当前前端静态内容边界

以下内容是展示层静态配置或演示数据，不应作为生产安全事实：

- desktop/src/data/staticAssets.ts、events.ts、app/display.tsx 中的名称、颜色、标签和枚举字典。
- desktop/src/data/range.ts 与 RangePage.tsx 中的 AgentRange 演示场景、重放命令和示例文本。
- desktop/src/bridge.ts 中浏览器预览所需的空数组、默认值或 mock 治理数据。
- JSX 中的默认分页、轮询间隔、空状态文案和按钮标签。

Tauri 桌面端的生产页面应以 Gateway/SQLite 返回的数据为准。静态字典可以保留用于显示，但 Agent、资源、事件、检测、决策、阻断和攻击链不能用前端 mock 补齐。若接口不可用，应显示“数据不可用/连接失败”，而不是显示为零或正常。

## 9. 下一阶段目标与验收标准

### P0：先保证闭环可用

1. Agent 列表补充 AgentType ID 过滤，并统一 Agent/资源/事件的筛选字段。
2. 增加 SQL 级 runtime-event-summary，区分原始事件统计与检测统计。
3. 将运行时策略矩阵入库，支持 observe/enforce、版本、审计和 executor 健康检查。
4. 明确每种 executor 的真实执行结果；would_block 不得显示为 blocked。
5. 响应成功后事务性同步 Detection、Attack chain 和 response action。
6. 完成 Windows 进程守护安装按钮的管理员权限、服务安装、离线失败和进程树验证。

### P1：补齐可运营性

1. 增加 discovery-runs、periodic-scan-runs、runtime-sessions 详情与游标分页。
2. 将 runtime-detections 的 source 过滤下推 SQL，消除最多 5000 条的隐式截断。
3. 改善攻击链详情的 N+1 查询，并支持按时间/AgentType 重建及可取消上下文。
4. 建立资源与 Agent、扫描、finding 的稳定外键和关系接口。
5. 让周期 Watcher 扫描也生成可查询的 Job/run 记录，或在页面上明确区分周期 run 与手动 Job。

### 最终验收

- 页面上的 Agent、资源、事件、Detection、决策、阻断和攻击链均来自数据库真实记录。
- 自动采集、手动检测、历史重放、策略评估、执行结果和回滚均可追踪到 Job/事件/响应 ID。
- “检测到风险”“策略决定阻断”“执行器已阻断”三种状态清晰可区分。
- 攻击链能解释触发检测、证据事件、上下文事件、决策和响应结果。
- 筛选、分页、汇总和时间范围在后端语义一致，不依赖前端静态数据或当前页累加。
- 失败、超时、取消和权限不足都有可见原因，并且不会伪装成成功或安全。
