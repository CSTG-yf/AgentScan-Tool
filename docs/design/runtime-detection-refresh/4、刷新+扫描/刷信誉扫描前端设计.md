# 前端扫描与刷新设计疑问文档

日期：2026-09-05

## 已确认方向

1. 不新增左侧菜单页面。
2. “扫描与刷新策略”放在现有 **Agent 治理中心** 内部，建议作为一个独立 tab。
3. 页面视觉参考静态资源检测页：白色背景、顶部统计卡片、内容区白色卡片、深色主按钮、低饱和状态标签。
4. 前端必须明确区分：
   - **刷新数据**：只调用查询接口，从数据库读取已有数据。
   - **重新扫描 / 重放 / 重建**：调用 Job 接口，让 Go 后端产生新数据。

- `docs/design/mockups/scan-refresh-governance-tab-normal.svg`

## 页面结构建议

### 1. 顶部统计卡片

建议展示 4 个指标：

| 指标 | 说明 | 数据来源 |
| --- | --- | --- |
| 后端扫描策略 | 当前可配置的扫描任务类型数量 | 后续 `GET /api/v1/scan-schedules`；当前可本地枚举 |
| 已启用扫描触发 | watcher、scheduler 等已开启数量 | 当前 `GET /api/v1/static-resource-scan-settings` |
| 自动刷新页面 | 开启自动刷新的页面数量 | 当前 `GET /api/v1/desktop-scan-schedule` |
| 最近扫描任务 | 最近 Job 状态和进度 | `GET /api/v1/jobs?limit=1` 或当前运行 Job 状态 |

### 2. 后端扫描策略区

用于配置真实扫描能力。

当前可展示：

- 文件变化实时扫描：`realtimeEnabled`
- 定时兜底复扫：`rescanEnabled`
- 实时扫描防抖：`debounceMs`
- Credential / MCP / Skill / Plugin / Prompt / Environment 的复扫间隔

当前接口：

| 操作 | 接口 |
| --- | --- |
| 查询静态资源扫描配置 | `GET /api/v1/static-resource-scan-settings` |
| 保存静态资源扫描配置 | `PUT /api/v1/static-resource-scan-settings` |

后续理想接口：

| 操作 | 接口 |
| --- | --- |
| 查询所有扫描计划 | `GET /api/v1/scan-schedules` |
| 修改某类扫描计划 | `PUT /api/v1/scan-schedules/{task_type}` |

### 3. 手动扫描任务区

这里是“产生新数据”的入口。

建议任务：

| 按钮 | 后端行为 | 当前可用接口 |
| --- | --- | --- |
| Agent 发现 | 重新枚举 Agent 实例 | `POST /api/v1/jobs`，`kind=agent_discovery` |
| 静态资源扫描 | 扫描静态资源和 finding | `POST /api/v1/jobs`，`kind=resource_scan` |
| 事件检测重放 | 基于行为事件重新生成异常检测 | `POST /api/v1/jobs`，`kind=event_replay` |
| 攻击链重建 | 基于检测和证据重建攻击链 | `POST /api/v1/jobs`，`kind=attack_chain_rebuild` |

按钮状态建议：

- 有同类 Job 正在运行时，当前按钮显示“扫描中”。
- 其他可能冲突的扫描按钮禁用。
- 展示最近 Job 的 `job_id`、`status`、`phase`、`current/total`、`progress`。
- Job 完成后自动执行一次“刷新数据”。

### 4. 前端自动刷新策略区

用于配置页面读接口的刷新频率。

当前接口：

| 操作 | 接口 |
| --- | --- |
| 查询页面刷新配置 | `GET /api/v1/desktop-scan-schedule` |
| 保存页面刷新配置 | `PUT /api/v1/desktop-scan-schedule` |

注意：这个接口当前名字带有 `scan`，但前端语义更像“页面刷新间隔”。后续建议改为：

| 操作 | 建议接口 |
| --- | --- |
| 查询页面刷新配置 | `GET /api/v1/page-refresh-settings` |
| 保存页面刷新配置 | `PUT /api/v1/page-refresh-settings` |

页面刷新建议：

| 页面 | 默认间隔 | 主要数据域 |
| --- | --- | --- |
| 安全总览 | 10 秒 | `agents`, `static_resources`, `runtime_detections`, `runtime_attack_chains` |
| Agent 检测 | 15 秒 | `agents` |
| 静态资源检测 | 10 秒 | `static_resources`, `scan_findings` |
| 事件检测 | 8 秒 | `runtime_detections` |
| 攻击链 | 10 秒 | `runtime_attack_chains` |
| 行为追踪 | 15 秒 | `behavior_events` |
| 告警中心 | 10 秒 | `runtime_detections`, `runtime_response_actions` |
| 靶场状态 | 30 秒 | `range_status` |

## 前端刷新流程

### 自动刷新

推荐流程：

```text
页面进入 / 定时器触发
        ↓
读取当前页面刷新配置
        ↓
GET /api/v1/changes?cursor=&domains=
        ↓
如果相关数据域变化
        ↓
调用当前页面列表 / 汇总 / 详情查询接口
```

设计要点：

- 每个页面使用自己的刷新间隔。
- 页面不在前台时可以暂停或降低频率。
- 如果接口连续失败，应退避，不要持续高频请求。
- 打开详情抽屉时，默认只刷新列表和汇总，不自动替换用户正在看的详情内容。

### 手动刷新

手动刷新只读数据库：

```text
用户点击“刷新数据”
        ↓
调用当前页面查询接口
        ↓
更新列表 / 汇总 / 当前筛选结果
```

不应该调用：

- `POST /api/v1/jobs`
- 单资源 scan trigger
- watcher 相关扫描函数

### 手动扫描

手动扫描会创建 Job：

```text
用户点击“开始扫描”
        ↓
POST /api/v1/jobs
        ↓
轮询 GET /api/v1/jobs/{job_id}
        ↓
完成后调用当前页面“刷新数据”
```

## 页面接口使用说明

### 静态资源检测页

| 用途 | 接口 |
| --- | --- |
| Agent 列表 / 左侧筛选 | `GET /api/v1/static-resources/agents` |
| 资源列表 | `GET /api/v1/static-resources` |
| 资源详情 | `GET /api/v1/static-resources/{resource_id}` |
| findings | `GET /api/v1/static-resources/{resource_id}/findings` |
| 手动资源扫描 | `POST /api/v1/jobs`，`kind=resource_scan` |
| 汇总/刷新判断 | `GET /api/v1/changes?domains=static_resources,scan_findings,scan_jobs` |

### 事件检测页

| 用途 | 接口 |
| --- | --- |
| AgentType 汇总 | `GET /api/v1/runtime-detections/summary/agent-types` |
| 异常事件列表 | `GET /api/v1/runtime-detections` |
| 异常事件详情 | `GET /api/v1/runtime-detections/{detection_id}` |
| 手动重放检测 | `POST /api/v1/jobs`，`kind=event_replay` |
| 刷新判断 | `GET /api/v1/changes?domains=runtime_detections,behavior_events,scan_jobs` |

### 攻击链页

| 用途 | 接口 |
| --- | --- |
| AgentType 汇总 | `GET /api/v1/attack-chains/summary/agent-types` |
| 攻击链列表 | `GET /api/v1/attack-chains` |
| 攻击链详情 | `GET /api/v1/attack-chains/{attack_chain_id}` |
| 手动重建攻击链 | `POST /api/v1/jobs`，`kind=attack_chain_rebuild` |
| 刷新判断 | `GET /api/v1/changes?domains=runtime_attack_chains,runtime_attack_chain_events,scan_jobs` |

## 待确认问题

### 1. 页面入口

建议：不新增左侧菜单，把“扫描与刷新策略”放入 Agent 治理中心 tab。

待确认：

- tab 名称是否确定为“扫描与刷新策略”？
- 是否需要放在“扫描方案”后面、“决策与动作”前面？

### 2. `desktop-scan-schedule` 的语义

当前接口名像“扫描计划”，但前端实际更适合用来保存“页面刷新间隔”。

待确认：

- 是否接受短期继续用 `desktop-scan-schedule`？
- 是否要新增 `page-refresh-settings`，把刷新配置从扫描配置中拆出来？

### 3. 后端扫描计划接口

目前静态资源扫描配置已有接口，但 Agent 发现、事件检测、攻击链是否都需要独立自动扫描间隔还没有统一配置入口。

待确认：

- 是否新增 `GET/PUT /api/v1/scan-schedules`？
- `scan_schedules` 是否按 `task_type` 配置？
- 静态资源的细分间隔是否保留在 `static-resource-scan-settings`？

### 4. Job 状态枚举

当前可能出现 `completed`、`success`、`failed`、`cancelled`、`preview` 等状态。

待确认：

- 前端展示时是否统一把 `completed/success` 显示为“成功”？
- 是否后端统一状态枚举为 `queued/running/completed/failed/cancelled`？

### 5. 触发来源命名

推荐标准：

- `manual`
- `scheduler`
- `watcher`

待确认：

- 当前已有 `schedule` 是否改为 `scheduler`？
- 是否需要保留兼容展示？

### 6. 并发策略

待确认：

- 同类扫描运行时，重复点击是返回已有 Job，还是提示“已有任务运行中”？
- Agent 发现和静态资源扫描是否允许同时运行？
- 单资源扫描和全量静态资源扫描是否互斥？

### 7. 详情抽屉刷新策略

待确认：

- 用户打开异常事件详情或攻击链详情时，自动刷新是否更新抽屉内容？
- 如果详情对应对象被删除或状态改变，是否显示提示条？
- 是否需要“刷新详情”按钮？

### 8. 最近 Job 展示

待确认：

- 页面是否只展示最近一个 Job？
- 是否需要小型 Job 历史列表？
- 是否需要跳转到未来独立的 Scan Task 页？

### 9. Summary 接口展示

事件检测和攻击链已经有 AgentType 汇总接口。

待确认：

- “扫描与刷新策略”页是否也需要展示这些 summary 的状态，还是只展示刷新配置？
- 顶部统计卡片是否使用真实接口返回，还是先使用配置计数？

### 10. 权限与失败反馈

待确认：

- 修改后端扫描配置是否需要管理员权限或 Gateway token？
- 保存失败时是否保留本地 UI 修改，还是回滚到接口返回值？
- 扫描 Job 失败后是否自动展开错误详情？

## 推荐实现顺序

1. 先按 mockup 在 Agent 治理中心内增加“扫描与刷新策略”tab。
2. 短期复用现有接口：
   - `desktop-scan-schedule`
   - `static-resource-scan-settings`
   - `jobs`
   - `changes`
3. 前端 UI 上先把“后端扫描”和“前端刷新”语义拆清楚。
4. 后端补齐 `scan-schedules` 后，再替换旧配置来源。
5. 最后把 App 里的固定 3 秒 changes 轮询改造成按页面配置驱动。
