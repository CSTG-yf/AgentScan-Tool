# Go 后端扫描与 Job 机制设计

日期：2026-09-05

## 设计目标

后端负责“真实检测系统”，也就是发现系统状态变化、执行扫描、产生新数据，并把结果写入数据库。前端刷新不应该触发扫描，除非用户明确点击“重新扫描 / 重放检测 / 重建攻击链”等扫描动作。

核心原则：

> 扫描 = 从系统产生新数据；刷新 = 从数据库读取已有数据。

## 当前已有能力

当前项目已经具备一部分基础设施：

| 能力 | 当前接口 / 文件 | 说明 |
| --- | --- | --- |
| 统一 Job 入口 | `POST /api/v1/jobs` | 已支持 Agent 发现、静态资源扫描、事件重放、攻击链重建 |
| Job 查询 | `GET /api/v1/jobs`、`GET /api/v1/jobs/{job_id}` | 查询扫描任务历史和详情 |
| Job 取消 | `POST /api/v1/jobs/{job_id}/cancel` | 取消未结束任务 |
| 变化游标 | `GET /api/v1/changes` | 返回变化的数据域，供前端判断是否需要刷新 |
| 静态扫描配置 | `GET/PUT /api/v1/static-resource-scan-settings` | 控制 watcher、定时复扫、防抖和资源类型间隔 |
| 桌面刷新 / 扫描间隔配置 | `GET/PUT /api/v1/desktop-scan-schedule` | 当前命名偏混合，既像前端刷新间隔，也被后端 Agent discovery scheduler 使用 |
| 异常事件汇总 | `GET /api/v1/runtime-detections/summary/agent-types` | 按 AgentType 聚合异常事件 |
| 攻击链汇总 | `GET /api/v1/attack-chains/summary/agent-types` | 按 AgentType 聚合攻击链 |

`POST /api/v1/jobs` 当前支持的 `kind`：

| kind | 兼容别名 | 作用 |
| --- | --- | --- |
| `agent_discovery` | `agents` | 重新构建 Agent inventory |
| `resource_scan` | `static_resources` | 扫描单个资源或某个 Agent 下的静态资源 |
| `event_replay` | `detection_replay` | 基于行为事件重放异常检测 |
| `attack_chain_rebuild` | `chain_rebuild` | 重建攻击链 |

## 目标模型

后端扫描应抽象成三层：

```text
Manual / Scheduler / Watcher
          ↓
      Scan Job
          ↓
   Task Runner Registry
          ↓
      Scan Engine
          ↓
      Database
          ↓
   Change Domains
```

### 任务类型

推荐统一使用 `task_type` 表达扫描对象。为了兼容现有实现，短期可以继续接收 `kind`，但内部应逐步向 `task_type` 收敛。

| task_type | 说明 | 主要写入 |
| --- | --- | --- |
| `agent_discovery` | Agent 发现与实例归档 | `agents` |
| `static_assets` | 静态资源扫描 | `static_resources`、`scan_findings` |
| `runtime_detections` | 异常事件检测或历史重放 | `runtime_detections` |
| `attack_chains` | 攻击链构建或重建 | `runtime_attack_chains`、`runtime_attack_chain_events` |
| `behavior_trace` | 行为事件采集与聚合 | `behavior_events` |
| `environment` | 环境状态检测 | `environment`、`range_status` |

### 触发来源

所有任务统一记录触发来源：

| trigger | 说明 |
| --- | --- |
| `manual` | 用户点击按钮触发 |
| `scheduler` | 后端定时任务触发 |
| `watcher` | `fsnotify` 等事件监听触发 |

当前代码里有 `schedule` 命名，建议后续统一为 `scheduler`，读取时兼容旧值。

### 扫描模式

| mode | 说明 |
| --- | --- |
| `full` | 全量扫描 |
| `incremental` | 增量扫描 |
| `single` | 单对象扫描 |
| `replay` | 基于历史事件重放 |
| `rebuild` | 重建派生数据，例如攻击链 |
| `scheduled` | 当前已有值，后续建议只作为兼容值 |

## 数据库设计

### scan_jobs

`scan_jobs` 是扫描执行记录，应保留为核心表。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `job_id` | Job ID，对外暴露 |
| `task_type` / `kind` | 扫描对象类型，短期保留 `kind` 兼容 |
| `mode` | 扫描模式 |
| `trigger` | `manual` / `scheduler` / `watcher` |
| `status` | `queued` / `running` / `completed` / `failed` / `cancelled` |
| `scope_json` | 扫描范围 |
| `result_json` | 扫描结果摘要 |
| `phase` | 当前阶段，如 `loading`、`scanning`、`writing` |
| `current` / `total` | 进度计数 |
| `progress` | 0-100，可由 current/total 推导 |
| `cancel_requested` | 是否请求取消 |
| `idempotency_key` | 幂等键，避免重复提交 |
| `created_at` / `started_at` / `finished_at` / `updated_at` | 生命周期时间 |
| `error` | 失败原因 |

### scan_schedules

建议新增统一的后端自动扫描配置表：

```sql
CREATE TABLE scan_schedules (
  task_type TEXT PRIMARY KEY,
  enabled INTEGER NOT NULL DEFAULT 1,
  interval_sec INTEGER NOT NULL,
  mode TEXT NOT NULL DEFAULT 'incremental',
  scope_json TEXT,
  updated_at TEXT NOT NULL,
  updated_by TEXT
);
```

说明：

| 字段 | 说明 |
| --- | --- |
| `task_type` | `agent_discovery`、`static_assets` 等 |
| `enabled` | 是否启用自动扫描 |
| `interval_sec` | 该任务自己的扫描间隔 |
| `mode` | 默认扫描模式 |
| `scope_json` | 可选范围，例如 Agent、路径、资源类型 |

静态资源的 credential、MCP、Skill 等细分间隔可以继续保留在 `static-resource-scan-settings` 中，也可以后续逐步迁移成 `scan_schedules.scope_json` 里的子策略。

## 推荐接口

### 查询扫描调度配置

`GET /api/v1/scan-schedules`

返回：

```json
{
  "items": [
    {
      "task_type": "agent_discovery",
      "enabled": true,
      "interval_sec": 900,
      "mode": "incremental",
      "scope": {}
    }
  ]
}
```

### 修改某类扫描调度

`PUT /api/v1/scan-schedules/{task_type}`

请求：

```json
{
  "enabled": true,
  "interval_sec": 900,
  "mode": "incremental",
  "scope": {
    "agent_type_id": 1
  }
}
```

### 手动创建扫描 Job

继续使用现有入口：

`POST /api/v1/jobs`

推荐请求：

```json
{
  "task_type": "static_assets",
  "kind": "resource_scan",
  "mode": "full",
  "trigger": "manual",
  "scope": {
    "agent_id": "agent-demo",
    "resource_type": "skill"
  },
  "idempotency_key": "manual-static-assets-agent-demo-20260905-001"
}
```

兼容规则：

- 新前端优先传 `task_type`。
- 旧前端可以继续传 `kind`。
- 后端内部统一归一化成一个 canonical task type。

### 查询 Job 历史

`GET /api/v1/jobs?kind=resource_scan&status=running&limit=100&offset=0`

后续建议兼容：

`GET /api/v1/jobs?task_type=static_assets&trigger=manual&status=running`

### 查询 Job 详情

`GET /api/v1/jobs/{job_id}`

返回中必须包含：

```json
{
  "job_id": "job-static-assets-001",
  "task_type": "static_assets",
  "kind": "resource_scan",
  "mode": "full",
  "trigger": "manual",
  "status": "running",
  "phase": "scanning",
  "current": 64,
  "total": 100,
  "progress": 64,
  "scope": {},
  "result": {}
}
```

### 取消 Job

`POST /api/v1/jobs/{job_id}/cancel`

取消后：

- `cancel_requested=true`
- `status=cancelled`
- `finished_at` 写入当前时间
- 正在运行的 runner 通过 context 停止

### 查询变化域

`GET /api/v1/changes?cursor=123&domains=agents,static_resources,scan_jobs`

返回：

```json

  "next_cursor": 124,
  "changed_domains": ["static_resources", "scan_findings", "scan_jobs"],
  "latest_at": "2026-09-05T10:00:00Z",

```

推荐数据域：

| domain | 说明 |
| --- | --- |
| `agents` | Agent inventory 变化 |
| `static_resources` | 静态资源变化 |
| `scan_findings` | 静态风险结果变化 |
| `behavior_events` | 行为事件变化 |
| `runtime_detections` | 异常事件变化 |
| `runtime_attack_chains` | 攻击链变化 |
| `scan_jobs` | Job 状态变化 |

## 调度器设计

后端启动时加载 `scan_schedules`，为每个启用任务注册定时器。

执行规则：

1. 每种 `task_type` 拥有自己的 interval。
2. 到期后检查同类任务是否已有 `queued/running`。
3. 若已有运行中任务，本次跳过或延后。
4. 创建 `scan_jobs`，`trigger=scheduler`。
5. 执行统一 runner。
6. 完成后写入业务表和 `scan_jobs`，并写入 change log。

伪流程：

```text
load scan_schedules
  ↓
for each enabled schedule
  ↓
tick by interval_sec
  ↓
dedupe running task_type
  ↓
POST internal job: trigger=scheduler
  ↓
runner executes
  ↓
write database + change domains
```

## Watcher 设计

`fsnotify` 只负责发现变化，不直接写最终业务结果。

推荐流程：

```text
file changed
  ↓
debounce
  ↓
normalize resource scope
  ↓
create scan job
  trigger=watcher
  mode=incremental or single
  ↓
static asset runner
  ↓
write static_resources / scan_findings
  ↓
write changes
```

注意点：

- 同一个资源短时间多次变化必须合并。
- watcher Job 也要出现在 `/api/v1/jobs`。
- watcher 不应绕过 `scan_jobs`，否则前端无法统一展示扫描历史。

## 并发与幂等

建议规则：

| 场景 | 处理 |
| --- | --- |
| 同类全量扫描正在运行 | 拒绝或返回已有 Job |
| 单资源扫描正在运行 | 相同资源合并，不同资源可并发，视扫描器能力而定 |
| 前端重复点击 | 使用 `idempotency_key` 返回同一 Job |
| scheduler 与 manual 冲突 | manual 优先；scheduler 可跳过当前 tick |
| watcher 高频事件 | debounce + scope 合并 |

## 前端关联

后端扫描完成后，必须能让前端知道哪些页面需要刷新：

| task_type | changed_domains |
| --- | --- |
| `agent_discovery` | `agents`, `scan_jobs` |
| `static_assets` | `static_resources`, `scan_findings`, `scan_jobs` |
| `runtime_detections` | `runtime_detections`, `behavior_events`, `scan_jobs` |
| `attack_chains` | `runtime_attack_chains`, `runtime_attack_chain_events`, `scan_jobs` |
| `environment` | `environment`, `range_status`, `scan_jobs` |

前端可以先轮询 `/api/v1/changes`，发现当前页面关心的数据域变化后，再调用页面查询接口。

## 迁移建议

1. 保留现有 `/api/v1/jobs`，补充 `task_type` 字段兼容。
2. 新增 `/api/v1/scan-schedules`，不要继续把后端扫描配置塞进 `desktop-scan-schedule`。
3. 将当前 `RunBackgroundJobs` 中的 Agent discovery 定时逻辑迁移到通用 scheduler registry。
4. 让 watcher 触发的扫描也生成标准 `scan_jobs`。
5. 前端页面保留“刷新数据”和“重新扫描”两个按钮，分别调用查询接口和 Job 接口。
6. 后续再把 `desktop-scan-schedule` 改名或迁移为前端 `page-refresh-settings`。
