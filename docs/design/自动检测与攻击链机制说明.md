# 自动检测、手动检测与攻击链机制说明

## 1. 文档目的

本文明确以下概念和边界：

1. “自动检测/手动检测”分别属于 Go 后端安全检测，还是前端数据库数据同步。
2. 自动检测和手动检测分别作用于哪些对象。
3. 攻击事件、异常阻断、攻击链之间的处理顺序和数据关系。
4. 当前实现与目标实现之间的差异，以及后续验收标准。

本文中的“当前实现”以 Gateway、检测引擎、SQLite 和 Tauri 桌面端的实际代码为准；“目标实现”是为了满足完整可运营闭环而提出的改进方案。

---

## 2. 总体结论

系统需要两套策略，但不能把两套策略都称为“自动检测/手动检测”：

- **Go 后端**负责真正的发现、扫描、运行时检测、策略决策、阻断和攻击链生成。这一层使用“自动检测/手动检测”。
- **前端**负责调用后端接口读取数据库事实并更新页面。这一层应使用“自动同步/手动刷新”，不应把普通的 GET 查询称为检测。

系统的安全主链路为：

```text
Agent 发现/资源枚举
        ↓
运行时事件采集并持久化
        ↓
检测引擎（原子规则 + 关联规则）
        ↓
策略引擎（allow / audit / alert / confirm / block）
        ↓
执行器（网络、Hook、Guardrail、MCP、进程等）
        ↓
响应结果持久化
        ↓
攻击链生成或更新
        ↓
前端通过查询接口展示
```

数据库是 Agent、静态资源、运行时事件、检测结果、决策、响应动作和攻击链的事实来源。

---

## 3. 两层自动/手动策略

### 3.1 Go 后端：真正的安全检测和处置

Go 后端的自动策略由后台任务、Watcher、事件接收器和策略引擎触发；手动策略由 API 或 Job 显式触发。

| 后端能力 | 自动策略 | 手动策略 | 结果 |
| --- | --- | --- | --- |
| Agent 发现 | 后台发现任务、进程/文件/目录规则检查 | 创建 `agent_discovery` Job 或调用 Agent 扫描接口 | 更新 Agent 库存和运行状态 |
| 静态资源 | Watcher 周期枚举、快照和扫描 | 单资源扫描或批量重扫 Job | 更新资源、扫描记录和 findings |
| 运行时事件 | Hook、Guardrail、Proxy、OS Sensor 上报后立即评估 | 提交单条/批量事件，或历史事件重放 | 写入事件并产生 Detection |
| Detection | 每条新事件自动执行原子/关联规则 | `event_replay`、`detection_replay` 或规则升级后的重评估 | 更新 Detection 和证据关联 |
| 决策/阻断 | 策略引擎自动生成决策并派发执行器 | 手动预览、执行阻断、重试或回滚 | 记录响应动作及实际结果 |
| 攻击链 | Detection 满足建链条件后自动建链 | `attack_chain_rebuild` Job | 创建或重建攻击链投影 |

后端手动操作不是“绕过检测”，而是“显式要求后端执行一次检测或处置任务”。所有手动任务都应有 Job ID、状态、开始/结束时间和失败原因。

### 3.2 前端：数据库数据同步和页面刷新

前端的自动/手动策略只负责获取已经存在的后端数据：

| 前端动作 | 实际行为 | 是否执行检测 |
| --- | --- | --- |
| 自动同步 | 轮询 `/api/v1/changes`，发现域变化后重新 GET 当前页面数据 | 否 |
| 手动刷新 | 重新调用列表/详情 GET 接口 | 否 |
| 立即发现 Agent | 调用后端 Job 接口并等待任务状态 | 是，由后端执行 |
| 立即扫描资源 | 调用资源扫描接口并等待 Job | 是，由后端执行 |
| 重放事件 | 调用事件重放 Job | 是，由后端重新评估 |
| 重建攻击链 | 调用攻击链重建 Job | 是，由后端重放链投影 |
| 执行阻断 | 调用 block action 接口 | 是处置动作，不是页面刷新 |

因此，页面上应把以下按钮分开：

- `自动同步`：控制页面是否自动读取数据库变化。
- `刷新数据`：只重新查询当前数据。
- `立即发现 Agent`：触发后端发现任务。
- `立即扫描资源`：触发后端静态扫描任务。
- `重放事件`：对历史事件重新执行检测。
- `重建攻击链`：重建持久化攻击链。
- `预览阻断` / `执行阻断` / `回滚阻断`：操作响应动作。

不要使用一个全局的“自动检测开关”同时控制前端刷新和后端检测；这会导致用户误以为刷新页面会重新扫描系统。

## 4. 检测对象定义

自动/手动检测的对象不只是 Agent 信息和 Agent 静态资源，至少包括以下六类对象。

### 4.1 Agent 信息

检测含义是“发现和确认 Agent 是否存在、是否运行以及运行状态是否可信”，包括：

- Agent 类型和类型 ID。
- 安装路径、工作目录和配置位置。
- 进程 PID、运行状态和版本信息。
- 发现置信度、最后发现时间和缺失状态。

Agent 发现是库存检测，不等于攻击检测。

### 4.2 Agent 静态资源

静态资源检测用于识别 Agent 运行前或运行期间可被加载的文件和配置，例如：

- Skill、Plugin、MCP 配置和服务器目录。
- Agent 配置文件、提示词模板和规则文件。
- 工作区文件、脚本、可执行文件和依赖清单。
- 凭据配置、网络配置和其他敏感资源。

典型流程为：

```text
资源枚举 → 快照/哈希 → 判断是否变化 → 预扫描策略
→ 扫描器 → findings/risk → 后处理策略 → 持久化扫描结果
```

### 4.3 运行时事件

运行时事件是安全检测的主要输入，来源包括：

- Agent Hook。
- Guardrail。
- Proxy 或网络出口。
- Windows/OS Sensor。
- 外部连接器和批量事件上报接口。

**所有事件都应先保存，包括正常事件、可疑事件、攻击事件和已阻断事件。** 正常事件虽然通常不会单独产生 Detection，但它们是审计、时间线和攻击链上下文的重要依据。

### 4.4 Detection

Detection 是检测引擎对运行时事件作出的安全判断，不等同于原始事件。

- 原子规则：单个事件即可命中，例如敏感文件访问、危险命令、提示注入。
- 关联规则：多个事件组合命中，例如凭据读取后网络外传、Shell 下载后写入并执行。
- Detection 保存严重度、置信度、规则版本、检测类型和事件证据。

### 4.5 决策和响应动作

策略引擎根据 Detection 的类别、严重度和置信度生成决策：

- `ALLOW`：允许继续。
- `AUDIT`：仅记录。
- `ALERT`：告警。
- `CONFIRM`：需要确认。
- `BLOCK`：策略要求阻断。

`BLOCK` 只是策略决定，不代表执行器已经成功阻断。响应动作还要记录：

- `planned`：已规划。
- `would_block`：观察模式下模拟会阻断。
- `dispatched`：已派发执行器。
- `executed`：执行器确认成功。
- `failed`：执行失败。

### 4.6 攻击链

攻击链是对 Detection、证据事件、上下文事件、决策和响应结果的持久化关联，不是前端根据标题或字符串临时拼接出来的页面数据。

## 5. 运行时检测和阻断顺序

推荐的后端处理顺序如下：

1. 采集器提交规范化运行时事件。
2. Gateway 将事件写入 `behavior_events/runtime_events`。
3. 检测引擎读取当前事件和有限关联窗口。
4. 原子规则和关联规则生成或更新 Detection。
5. 策略引擎根据严重度、类别和置信度生成 Decision。
6. 在 `action/enforce` 模式下调用相应执行器；在 `observe` 模式下只记录 `would_block`。
7. 持久化 Response Action 的真实执行结果。
8. 创建或更新攻击链，并关联 Detection、Decision 和 Response。
9. 前端收到变更通知后重新查询权威数据。

事件必须在阻断之前入库。这样即使进程被终止、网络被切断或执行器失败，也能保留阻断前的证据。

当前默认运行时安全模式是 `observe`。只有切换到 `action`/`enforce` 后，策略允许的阻断动作才会真正执行。

路径黑名单的 `FILE_BLOCK` 执行点仅适用于 Codex、Claude Code 已接入且能力合同声明可阻断的同步 `PreToolUse` 文件读取 Hook。首次命中只产生证据；执行器从该事件提取规范化路径的 SHA-256，写入按连接器隔离的持久策略并读回确认。此后同一路径经受控 `Read`/`read_file` 或受支持的单条字面量读取命令再次进入 Hook 时，才会在读取前拒绝。`observe` 模式不会执行阻断；无可阻断的受控 Hook 证据、无法确定目标路径或策略存储失败时，响应必须报告失败，不能标记为已执行。Agent Hook 整工具阻断也须有该 Hook 的可阻断能力证据。已完成的首次读取、任意 OS `read(2)`、复杂 shell 命令以及未接入的 Agent 不受这一执行点保护。

Guardrail 的 `PROMPT_BLOCK` 执行器不尝试事后拦回已经发送的请求。它只核验同步代理在 Action 模式下选择“不向上游转发”分支时写入的内部回执；由 REST、Hook 或事后扫描上报的 `block` 结果即使内容相同，也不能凭此回执标记为已执行。缺少代理回执的 block 判定在统一事件中记为 `flagged` 而非 `blocked`；Observe 模式只保留待阻断判定。

## 6. 攻击链生成机制

### 6.1 攻击链不应以阻断成功为生成条件

攻击链和异常阻断有关，但两者不是同一个条件：

- **生成条件**：检测引擎确认存在符合建链条件的安全 Detection。
- **阻断条件**：策略引擎根据风险决定是否需要阻断。
- **链状态**：由响应动作的实际结果更新。

如果只在阻断成功后生成攻击链，会丢失以下重要情况：

- 观察模式下发现了攻击但尚未阻断。
- 策略要求阻断但执行器失败。
- 风险需要人工确认而暂未阻断。
- 某个攻击行为已经发生，但当前执行点无法回滚。

### 6.2 当前实现的建链方式

当前后端的攻击链投影具有以下特点：

1. 运行时事件写入后立即进入检测引擎。
2. 关联窗口默认是最近 10 分钟，最多使用 200 条事件。
3. 关联优先级为同一 `session`，其次是同一 `trace`，再其次是同一 Agent。
4. 只有符合建链条件的 Detection 才会创建 `runtime_attack_chains`。
5. 链身份主要由 `detection_id` 确定，重复命中会更新链的结束时间并去重事件关联。
6. 当前链事件主要是 Detection 的证据事件，而不是阻断前的全部事件。

当前典型建链类型包括：

- 提示注入驱动的数据外泄。
- 凭据外泄。
- 数据外泄。
- 运行时利用链。
- `attack + CRITICAL` 的高危攻击 Detection。

### 6.3 推荐的目标建链方式

攻击链中的事件应分为两层：

#### 证据事件（Evidence Events）

真正支持 Detection 的事件，例如：

- 提示注入。
- 敏感文件或凭据读取。
- 工具调用。
- Shell 执行。
- 下载、写文件和执行文件。
- 网络请求或外传。

#### 上下文事件（Context Events）

同一攻击范围内、阻断前发生的全部运行时事件，包括正常事件。

建议的范围定义为：

```text
同一 Agent/session/trace
+ 检测关联窗口内
+ 从首个相关事件开始
+ 到触发阻断的事件（或最后一个检测事件）结束
```

这样可以满足“阻断前所有事件都进入当前攻击链”的要求，同时避免把正常事件错误标记为攻击证据：

- 正常事件保存在 `context_events` 中。
- 安全相关事件保存在 `evidence_events` 中。
- Detection 只引用证据事件。
- 攻击链详情展示完整时间线。

### 6.4 攻击链状态

建议使用以下状态，而不是只使用 `active/contained`：

| 状态 | 含义 |
| --- | --- |
| `active` | 已检测到风险，尚未确认成功阻断 |
| `would_block` | 策略要求阻断，但当前处于观察模式 |
| `failed` | 已尝试阻断，但执行器失败 |
| `contained` | 执行器确认成功阻断或隔离 |
| `closed` | 事件窗口结束或人工关闭，但不代表成功阻断 |

`contained` 必须依据 Response Action 的成功结果更新，不能仅根据某个事件的字符串字段推断。

### 6.5 攻击链与阻断的关系

完整关系如下：

```text
事件 E1（正常）
  → 事件 E2（提示注入）
  → 事件 E3（读取凭据）
  → 事件 E4（网络外传）
  → Detection
  → Decision=BLOCK
  → Response Action=executed/failed/would_block
  → Attack Chain 状态更新
```

其中 E1 可以是正常事件，但它仍然可能是理解攻击过程所需的上下文。

阻断发生后，后续事件不应继续无条件加入同一条链；应根据新的 Session/Trace、时间窗口或新的 Detection 创建后续链，避免把阻断后的正常运行混入已处置链。

## 7. 手动操作的一致性要求

手动阻断不能只更新 Detection 状态，否则可能产生：

```text
Detection = mitigated
Attack Chain = active
Response Action = 不存在或状态不一致
```

手动阻断应由统一服务完成以下事务：

1. 记录或更新 Response Action。
2. 根据执行结果更新 Detection 状态。
3. 根据执行结果更新 Attack Chain 状态。
4. 写入审计事件。
5. 失败时保留错误原因并允许安全重试。

前端必须分别展示：

- 检测到风险。
- 策略决定阻断。
- 阻断动作已派发。
- 执行器已成功阻断。
- 阻断执行失败。

## 8. 推荐的前端页面呈现

### 8.1 Agent 页面

- `刷新数据`：只查询 Agent 列表。
- `立即发现 Agent`：创建发现 Job。
- 展示 Agent 状态、运行状态、最后发现时间、置信度和 Job 状态。

### 8.2 静态资源页面

- `刷新数据`：只查询资源和扫描结果。
- `立即扫描`：创建扫描 Job。
- 展示资源风险、最近扫描时间、扫描状态和 findings 数量。

### 8.3 运行事件/攻击事件页面

- `自动同步`：监听变更并刷新列表。
- `刷新数据`：重新查询当前页。
- `重放事件`：创建历史事件重放 Job。
- 事件表显示 `normal/abnormal/security/blocked` 等结果分类。

### 8.4 攻击链页面

- `刷新数据`：重新查询已持久化攻击链。
- `重建攻击链`：创建 `attack_chain_rebuild` Job。
- 链列表显示严重度、状态、Agent、Session/Trace、开始/结束时间、证据数和上下文数。
- 链详情按时间线展示：
  - 灰色：正常上下文事件。
  - 蓝色：支持证据事件。
  - 红色：触发事件。
  - 橙色：阻断决策或响应事件。

页面不得通过静态演示数据补齐空结果。接口不可用时，应显示“数据不可用/连接失败”，不能显示为 0 或“正常”。

## 9. 推荐的策略配置

前端同步策略和后端检测策略应独立配置。

### 9.1 前端同步策略

```json
{
  "auto_sync_enabled": true,
  "poll_interval_seconds": 3,
  "refresh_on_domain_change": [
    "agents",
    "resources",
    "events",
    "detections",
    "decisions",
    "chains",
    "jobs"
  ]
}
```

### 9.2 后端检测策略

```json
{
  "agent_discovery_enabled": true,
  "static_scan_enabled": true,
  "runtime_detection_enabled": true,
  "attack_chain_enabled": true,
  "runtime_security_mode": "observe"
}
```

其中：

- `runtime_detection_enabled` 控制事件是否进入 Detection Engine。
- `runtime_security_mode=observe` 只记录会阻断的决策。
- `runtime_security_mode=action` 才允许执行真实阻断。
- 攻击链生成应独立于是否成功阻断。

后续可进一步将运行时策略按 `agent_type_id`、事件类别、Detection 类型、严重度、置信度和执行器版本入库，实现可审计的策略版本管理。

## 10. 当前实现与目标实现差异

| 项目 | 当前实现 | 目标实现 |
| --- | --- | --- |
| 前端自动刷新 | 可轮询变更并重新查询 | 明确命名为自动同步，不触发检测 |
| Agent 检测 | 支持发现规则和发现 Job | 增加发现运行历史和统一过滤 |
| 静态资源检测 | 支持 Watcher、单资源扫描和批量重扫 | 所有周期扫描都有可查询 Run/Job |
| 运行时事件 | 事件写入后立即评估 | 保留全部事件并提供全事件统计 |
| 阻断模式 | 默认 observe，部分执行器能力有限 | 按执行器明确 executed/failed/would_block |
| 攻击链事件 | 主要保存 Detection 证据事件 | 同时保存证据事件和阻断前上下文事件 |
| 攻击链状态 | 主要是 active/contained | 根据响应动作支持 active/would_block/failed/contained/closed |
| 手动阻断同步 | 可能出现 Detection 与 Chain 状态不一致 | 统一事务同步 Detection、Response、Chain |
| 攻击链重建 | 支持 Job，但范围参数仍有限 | 支持 AgentType、时间范围、规则版本和可取消任务 |

## 11. 验收标准

### 检测层级

- 能明确区分后端检测和前端数据同步。
- 前端刷新不会触发发现、扫描、重放或攻击链重建。
- 每个手动检测动作都有可查询 Job 状态。

### 数据对象

- Agent、静态资源、运行时事件、Detection、Decision、Response 和 Attack Chain 均来自数据库真实记录。
- 正常事件不会被丢弃，也不会被误标记为攻击证据。
- Detection 能追溯到原始事件。

### 阻断

- `would_block` 不得显示为“已阻断”。
- 执行失败必须显示失败原因。
- 手动阻断成功后，Detection、Response 和 Attack Chain 状态一致。

### 攻击链

- 攻击链由 Detection 触发，不以阻断成功作为生成条件。
- 链详情能够展示触发事件、证据事件、上下文事件、决策和响应结果。
- 阻断前的正常事件可以作为上下文展示。
- 阻断后的无关事件不会无限加入原攻击链。

---

## 12. 最终定义

为了避免产品和研发理解不一致，后续统一采用以下定义：

> **自动检测**：Go 后端由事件、Watcher 或定时任务自动触发的发现、扫描、规则评估和处置流程。
>
> **手动检测**：用户通过前端按钮或 API 显式创建后端检测/重放/重建 Job。
>
> **自动同步**：前端根据变更通知或定时器自动读取数据库数据，不执行检测。
>
> **手动刷新**：前端重新调用查询接口，不执行检测。
>
> **攻击链**：以 Detection 为安全判断入口，关联证据事件、阻断前上下文事件、策略决策和响应结果的持久化安全对象。
>
> **异常阻断**：策略引擎对高风险 Detection 生成的处置决策及其执行结果；阻断结果决定攻击链状态，但不决定攻击链是否生成。
